Case study · Fall 2025

Autonomous maze-navigating robot

A two-motor Raspberry Pi Pico robot built in four stages: drive straight, run a timed course, build a maze for another team, then get through a maze on its own using two ultrasonic sensors. My first sensor approach failed completely, and a simpler rewrite finished the maze the next day.

The brief

Four tasks, each harder than the last:

TaskGoalOutcome
1Drive straight through a 120 cm × 30 cm corridor without touching a wallDone
2Run a pre-programmed course with a left and a right turn, with no sensors and no cableDone
3Build a cardboard maze from an assigned design for another team, in about a dayDone
4Navigate a maze using sensor feedback onlyDone

Hardware

The robot uses a kit acrylic chassis with two DC gear motors driven by an L298N dual H-bridge. Each motor gets a direction pair and a PWM enable pin from a Raspberry Pi Pico. For Task 4 we added two HC-SR04 ultrasonic sensors, one facing forward and one facing the right-hand wall.

We taped the first build together on purpose, so we could move components around and work out the layout before gluing. That caused a problem later (see below). We also watched other teams before committing. After seeing them struggle with weight distribution, we put our battery pack underneath, centred between the motors, in a 3D-printed mount.

Tasks 1–2: making two mismatched motors drive straight

Given the same PWM value, our two motors spun at noticeably different speeds, which is normal manufacturing variation for cheap DC motors. I tuned each one separately until the robot tracked straight:

# Duty cycle out of 65 535: the left motor needs ~19% more to match the right
def motor_a_forward(speed=35000):   # right motor, ~53%
    in1.high(); in2.low()
    ena.duty_u16(speed)

def motor_b_forward(speed=41500):   # left motor, ~63%
    in3.high(); in4.low()
    enb.duty_u16(speed)

  • Startup veer

    One motor kicked in harder than the other, so every run started with a swerve. I wrote a "priming" start that held both motors at a sub-threshold duty (≈13 000) before full speed. It didn't help.

  • Chassis flex

    The taped chassis bowed outwards under load, so the same code gave a different curve on every run. I tensioned a rubber band across the motor mounts as a stopgap. Once the makerspace restocked hot glue, we bonded the chassis permanently.

  • Working fix

    Because the veer was predictable, we started each run offset left and angled slightly left. That was enough to pass both tasks, but it wasn't very repeatable. I fixed it properly in Task 4.

For Task 2 I timed how long each motor needed to turn 90° at a fixed PWM value. Left and right turns came out different, since the motors didn't match. The course became a timed sequence: forward → left turn → forward → right turn → forward → stop.

Task 3: building a maze for someone else

We got a randomly assigned maze design on 17 November, due the next day. It had 10 cm walls, 30–35 cm paths, and angled turns of 110°, 150° and 120°. The tricky part wasn't the cardboard. It was the brief: dimensions were split across different sections and given in decimal inches, which made accurate measuring and cutting harder than it needed to be. We drew it in AutoCAD, cut the angled wall joints to match each turn, and delivered the maze and the drawing file to the receiving team on time.

Task 4: the sensor maze, and three days to solve it

This was the real test: no timed moves, only decisions based on what the sensors read. I started from a course-provided HC-SR04 driver and an open-source motor example, and wrote the navigation logic on top of them.

  • Attempt 1: build on the example code 2 Dec

    The code built on the starter example was slow to run, and after several hours it still had logic problems I couldn't fix.

  • Attempt 2: new logic, new sensor layout 2 Dec

    I rewrote the logic from scratch and moved the sensors to the left and right sides. It didn't make it past the first turn. I rolled back. The day ended with no progress.

  • Strip it back 3 Dec

    That night I spent about an hour cutting the code down instead of adding to it. I re-tuned turns and speeds, removed layers of conditions, and made the basic wall-following logic foolproof before anything else.

  • Maze complete 4 Dec

    It finished the maze about an hour and a half after we got to the lab, with only small timing tweaks. I added a stop condition for the end of the maze. The batteries died partway through (the robot had to be taken apart to swap them), and the drop in voltage changed how the motors behaved. A few re-runs later we got a clean, contact-free run.

How the final controller decides

The working version is a reactive, priority-ordered controller that follows the right-hand wall. Every loop it reads both sensors and takes the first rule that matches. It then makes a short drive pulse and pauses for 0.5 s, so the next reading is taken with the robot nearly still. A sensor timeout counts as 100 cm (open space).

Click a state

    The heart of it, trimmed for length:

    while True:
    front, side = get_front_distance(), get_side_distance()
    front = 100 if front < 0 else front      # timeout → open space
    side  = 100 if side  < 0 else side

    if side > 50 and front > 50:              # out of the maze
        stop_all(); sleep(8)

    if front < FRONT_DANGER:                  # 15 cm
        stop_all(); sleep(0.5)
        turn_left() if side < SIDE_MAX else turn_right()
    elif side < SIDE_MIN:                     # 7 cm: steer away
        pulse(SPEED_A, SPEED_B // 2)
    elif side > SIDE_OPTIMAL:                 # 10 cm: steer toward
        pulse(SPEED_A_TURN, SPEED_B_TURN)
    else:                                     # 7–10 cm: straight
        pulse(SPEED_A, SPEED_B, t=0.5)

    Simplified for readability. In the real file each branch writes its motor commands and timings out in full.

    Reflection

    The breakthrough came from deleting code, not writing more.

    • Simplify before you add. Each extra condition made the robot harder to predict. The version that worked had four rules and a clear order.
    • Know when to step back. On 2 December I kept trying to rescue approaches that weren't working. An hour of stripping the code down the next evening did more than the whole day of patching.
    • Test hardware and software together, early. Chassis flex and low batteries both changed how the code behaved. Calibration values are only valid for the hardware state they were tuned on.
    • Next time: wheel encoders and closed-loop speed control instead of timed turns, so the robot doesn't depend on battery voltage or hand-tuned PWM values.
